# Roadmap — Система управления требованиями

## Текущее состояние

Работающий прототип: загрузка PDF, извлечение требований (текст + изображения) через OpenRouter,
сохранение в PostgreSQL, просмотр в split-view (PDF + требования), accept/reject/edit,
метрика покрытия, экспорт Word/JSON/TXT, Docker-деплой.

**Реализовано:**
- Проекты -> Документы -> Разделы -> Требования (иерархия в БД)
- Обработка текста и изображений (multimodal AI)
- Review workflow: pending -> accepted / rejected / modified
- Аудит на уровне требования (ai_suggested vs human_edited)
- Метрика покрытия (processed pages, skipped pages, coverage %)
- Привязка требования к странице документа (page_number + навигация в UI)
- Развёртывание через Docker Compose (PostgreSQL + API + Frontend/Nginx)

## Этап 1 — Рабочий инструмент для инженера

**Приоритет:** критический | **Цель:** инженер может реально пользоваться системой

### 1.1 Качество извлечения
- [ ] Переработать промпт: отличать требования от позиций перечня комплектности
- [ ] Дифференциация приоритетов (не всё "Обязательно")
- [ ] Тестирование на размеченных примерах 
- [ ] Уведомление, если изображение не распознано или секция пуста

### 1.2 Расширенный жизненный цикл требования
- [ ] Статусы: извлечено -> верифицировано -> принято -> назначен ответственный -> в работе -> выполнено
- [ ] Назначение ответственного на требование
- [ ] Фильтрация по ответственному, по статусу жизненного цикла
- [ ] Bulk-операции (принять все / отклонить выбранные)

### 1.3 Справочники
- [ ] Типы требований (управляемый список, не свободный текст от AI)
- [ ] Приоритеты (управляемый список)
- [ ] Ответственные / пользователи
- [ ] Типы документов

### 1.4 UI: доработки
- [ ] Текстовый поиск по требованиям
- [ ] Подсветка bbox на странице PDF (точное место требования)
- [ ] Полноценный аудит-лог: фильтр "покажи все правки AI", "покажи все изменения человека"
- [ ] Статистика по проекту: сколько требований в каком статусе, кто отвечает за что

## Этап 2 — Diff версий документов

**Приоритет:** высокий 

> Сценарий: инженер загрузил ТТ -> требования легли в базу. Загрузил обновлённое ТТ
> по тому же проекту -> система показала: 12 новых требований, 3 противоречат ранее
> извлечённым, 8 дублируют. Инженер акцептовал 10, отклонил 2, уточнил 3.
> Всё сохранено, отслеживается, контролируется.

### 2.1 Модель версионирования
- [ ] Версии документов внутри проекта (v1, v2, ...)
- [ ] Привязка требований к конкретной версии документа
- [ ] Хранение diff-результата как сущности в БД

### 2.2 Алгоритм сравнения
- [ ] Семантическое сравнение требований 
- [ ] Категории: новые, удалённые, изменённые, дублирующие, противоречащие
- [ ] Порог сходства (настраиваемый)

### 2.3 UI diff
- [ ] Визуальное сравнение двух версий (side-by-side)
- [ ] Действия по каждому изменению: принять / отклонить / уточнить
- [ ] Сводка diff: N новых, N изменённых, N противоречащих

## Этап 3 — Верификация и контроль

**Приоритет:** средний 

### 3.1 Верификация значений
- [ ] Выделение числовых параметров (давление, температура, расход) из требований
- [ ] Сверка извлечённых значений с исходным текстом
- [ ] Подсветка расхождений

### 3.2 Аудит AI-действий
- [ ] Все изменения AI явно помечены в БД
- [ ] Пользователь может акцептовать / уточнить / отклонить каждую правку AI
- [ ] История изменений по каждому требованию (timeline)
- [ ] Отчёт: что добавлено AI vs что изменено человеком

### 3.3 Метрики и отчётность
- [ ] Dashboard по проекту: прогресс верификации, нагрузка по ответственным
- [ ] Экспорт отчётов для руководства
- [ ] Метрика: % требований, прошедших верификацию инженером

## Этап 4 — Масштабирование

**Приоритет:** низкий 

### 4.1 Пользователи и роли
- [ ] Аутентификация (логин/пароль или SSO)
- [ ] Роли: администратор, инженер, наблюдатель
- [ ] Разграничение доступа по проектам

### 4.2 Интеграции
- [ ] REST API для внешних систем
- [ ] Jira / YouTrack — автосоздание задач из требований
- [ ] Уведомления (email, Telegram)

### 4.3 Производительность и оптимизация пайплайна
- [ ] **Двухмодельная архитектура**: дешёвая модель для извлечения структуры документа (оглавление, разделы), сильная модель для анализа и извлечения требований — снижение стоимости при сохранении качества
- [ ] **Оптимизация пайплайна обработки**:
  - Эксперименты с параллелизмом (обработка нескольких разделов одновременно с ограничением rate limits)
  - Разбиение больших разделов на мелкие чанки для повышения точности и скорости
  - Адаптивный размер batch'ей в зависимости от размера раздела
- [ ] Кэширование результатов повторной обработки
- [ ] Поддержка больших документов (1000+ страниц) с прогресс-баром и возможностью паузы/возобновления
- [ ] Очередь задач (Celery / Redis) вместо синхронной обработки — фоновая обработка с уведомлениями

## Не в приоритете

Следующие пункты из старого роадмапа **сознательно отложены**, т.к. не создают ценности на текущем этапе:

- Поддержка DOCX/PPTX/TXT 
- Локальные AI-модели 
- Telegram-бот, массовая обработка ZIP
- Оптимизация стоимости API
